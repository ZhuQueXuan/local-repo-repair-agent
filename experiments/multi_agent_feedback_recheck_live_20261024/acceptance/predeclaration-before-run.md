# 真实反馈诊断与原会话返工验收

日期：2026-10-24。承接 [27](27_调研_多Agent主流模式对照与未完成项.md) 的第一优先项。本页在真实调用前建立，结果按实际运行追加，不改写原预声明。

## 目的与预声明

已有 C 真实题走过初修和首审，但首审直接 approve，未实际触发原会话返工。此次仅验证缺失接线：人工提供已知缺陷候选 → 修复模型在原会话确认候选 → 独立模型审查 → 如果确实 request_changes 则原会话返工一次 → 独立模型核查新版本 → 新副本重放与程序验收。若模型未要求返工或运行失败，保留结果，不重跑选优，也不改写成成功。

固定使用公开开发题 `split-after-boundary`，不称为新题、留出评价或模型自主发现。人工候选把旧 `yield list(it)` 改成 `rest = list(it); if rest and any(rest): yield rest`，会错误丢弃 `[0]`、`[None]`、`[False]`、`[0,0]` 这样的非空尾段。现有十项问题检查和四项上游针对性检查未覆盖此边界。

本次提前声明并公开六项附加诊断检查：上面四项假值尾段、普通非空尾段和空尾段；要求前五项保留非空尾段，空尾段不生成多余组。原题检查、原仓库及旧实验均保持。额外检查由独立子进程导入当前副本执行，计入本次程序验收，并随报告提供给审查者。因此即使审查提出了正确意见，也不能说模型在未知问题中独立发现缺陷。

只启动一个新身份，使用新面板显式“反馈流程验收（人工缺陷）”选项；默认仍是离线、单 Agent。策略固定于 `configs/multi_agent_feedback_diagnostic_v1.json`：父任务 30 分钟、阶段 300/120/180/90 秒、一次反馈窗口、连续格式错误或重复读取保护、无自动恢复/选优重跑。若初始模型提前改动人工候选，程序拒绝并保留失败，不偷偷还原。

真实请求沿用北邮首选、DeepSeek 官方备用及原共享账本。请求内容限公开题目、任务副本源码/补丁、程序检查结果、角色反馈和会话上下文；私有凭据只用于相应平台认证，不进入提示或成果。每逻辑请求每平台最多一次；转备用后本父任务保持备用；两边失败即停。项目既有无费用上限政策保持，所有角色记账；未知费用保留未知，不把占位当收费。此次不是 S/D/S+ 对照，不增加第三角色、RAG、动态委派或并发写仓库。

## 实现及边界

- `scripts/collaboration_diagnostic.py`：固定人工候选、严格原代码匹配、确认阶段源码哈希核对，以及六项实际进程检查；无任意种子路径或外部代码配置入口。
- `scripts/collaboration_live.py`：显式诊断才注入候选与确认提示；首审和最终审查仍由真实模型自行判断。修订复用现有 `RepairSession`，保留原问题、原历史及已执行提交的回执，不重新运行初修。诊断检查加入版本绑定的程序报告，旧版失败不被新版通过覆盖。
- 同时修正正式面板评分路径：评分器原本只允许 temp 输出，而双角色 runner 把输出指向正式 data 目录。现在在 `temp/task_service/<run_id>/collaboration-verification/` 执行评分，解析并核对退出码后再复制报告到正式成果目录；不放宽评分器目录权限。
- `scripts/collaboration_panel.py`、`collaboration_store.py`、`collaboration_panel.js`、`task_panel.html`：只增加固定诊断选择及来源说明。服务端限制题目、策略和模式，客户端不接受任意路径。正常双角色配置保持原样。

初始候选来源是人工，初始模型只确认；提示约束和事后哈希检查不等于 OS 只读沙箱。审查意见的引用/版本校验仍不等于完整的意见真伪裁决。此次新增程序检查只裁定已声明行为；通用独立裁决和 S+ 自查对照仍在后续范围。

## 同日后续：针对真实失败的离线修复

用户继续询问“是不是上下文设置太小、修好了吗”后，本轮开始实际修复上述衔接问题。这里的16,384是本项目`configs/deepseek_budget.json`的**消息JSON UTF-8字节保护**，不是16,384 token，也不是服务端报告的模型容量。原消息16,807字节在发送前被我们自己拦下，不能归因于模型窗口已满。它是早期保守策略，对携带额外审查交接的流程偏紧；本次先修复重复交接和近期记录无法进一步整理的实现缺口，未增加全局上限、修改单Agent默认或凭据/账本政策。

改动后的流程：

1. `collaboration_feedback.repair_feedback`将完整review/evidence按原内容保存在工作副本`temp/collaboration-feedback/`，消息只保留有界索引、全部finding ID、短预览、reviewed版本和文件SHA。提示明确完整内容要查文件，预览不当完整意见；固定测试命令也随本次返工提供。
2. `RepairModel.project_context`先走原投影；只有仍超全局保护线，才额外整理较早、已完成的工具交换，保留最近一组完整交换、原系统/任务、用户反馈和原始完整轨迹。只改变本次请求视图，不重新开始会话、重放命令或绕过硬保护。不可整理的过大任务仍会在HTTP/记账前停止。过程写入`repair-context-projections.json`。
3. 角色执行环境通过默认无行为变化的基类hook，将pytest缓存及TEMP/TMP放入工作副本temp。原源码manifest不放宽；其他新增文件继续拒绝。诊断初始提示补齐原manifest的测试命令，返工阶段明确结束“只确认不修改”的前一阶段约束。
4. 响应语义明确区分“原缺陷成立、我已修复”（accepted，后续仍需独立验证）和“原意见本身错误”（rejected，需能绑定目标版的证据）。不自动把模型写错的rejected改成accepted，也不把采纳当作已证实修复。

新增离线检查使用正式封存的旧`revising-trajectory.json`和最后一条原task-state消息，复现旧投影**恰好16,807字节**，再调用当前投影得到**13,154字节**，原消息逐字未变、原问题/反馈/最新交换与真实提交回执仍在；脚本化传输只调用一次。另有20KB不可整理输入仍不发请求、20条中文长意见完整归档而索引不超8KB、旧证据不能拒绝新版、真实pytest缓存归temp且未声明文件仍拒绝、子进程不继承凭据、完整脚本化返工/新版/重放等检查。

### Python支持范围澄清

“面向开源Python库”的准确含义是当前项目已接入和验证的任务范围，不能据此说助手只能写Python，也不能反过来宣称当前面板已支持任意语言。

- 核心动作是文件文本和Bash命令，协作角色、版本/证据、记账并无只能处理`.py`的协议约束；实现使用Python不等于目标代码必须是Python。
- 当前成品入口仍是固定登记任务；`collaboration_live.repair`要求按manifest导入Python包做预检，`check_task.py`使用Python包、unittest/pytest评分，`RepositoryRetrieval.__init__`明确只收集`.py`实现文件，符号解析使用Python AST。因此目前自动端到端验收确实按Python项目实现，不能直接把JS/Java仓库交给当前入口就宣称跑通。
