# 75 程序驱动的逐条独立复核：实现与离线验收

日期：2026-10-30。用户批准按[74诊断方案](74_诊断与方案_独立复核读取循环的流程与模型因素.md)实施，并明确先做离线检查、不继续付费测试。本轮源码版本为1.2.0-rc2，**仍是候选版，真实模型效果未验证**；当前运行中的旧面板没有重启或切换。默认仍仅分析，修复仍需用户另外启动。

## 改动解决什么问题

旧复核需要模型自己翻问题的JSON分页、安排代码读取、管理证据、逐条保存并最终总提交。74对三次真实失败的诊断发现：已读清单不能保证问题正文与依据持续同时可见；小样例即使材料齐全也多次不提交，因此不能只补回执或加时。

新版把机械推进交给程序：**冻结初稿 → 程序选一条并独立读取源码 → 完整材料的新会话 → 模型提交判断或请求一轮补证 → 程序保存本条、进入下一条 → 程序汇总。** 仍是分析者、复核者两个角色；每条新会话不意味着增加第三个角色，也不保证模型错误相互独立。

本轮没有执行74中的后续真实门槛，没有把旧失败改成成功，没有生成虚构的模型复核成绩。

## 已实现的行为

### 完整单条材料

- `ReviewCase.prepare`重新读取同一冻结快照，验证清单与文件哈希。小工程若所选文件整体放得下，就提供全部所选文件；分析者的`evidence_ids`不进入复核输入。
- 所选代码较大时，保留完整候选文字及全部原引用行段，并在可用空间内向两侧扩展最多12行。输入明确标注未提供文件、文件清单是否完整及范围限制，不宣称函数或全仓已通读。
- 核心messages上限11000 UTF-8字节，原平台messages硬上限16384字节保持。正文和原引用放不下时记“材料不足”，不静默截断、不要求模型凭残缺材料下结论。
- 每次判断请求重新提供完整当前材料；补证追加在原材料后，既有R编号和原问题正文不被移出。不再把878字符问题拆成800字符分页。

### 两个模型动作

`submit_case_review`提交支持、不支持或待验证、分类、理由、反例/替代解释、成立条件、建议及本条R引用。长哈希、来源、初稿身份和问题身份由程序绑定，模型不必回填。

`request_case_evidence`提出具体缺失问题和所选文件行段。每条只允许一轮补证；程序按完整范围组装，83行不再因80行工具限制反复拒绝。补证过大或重复索取已经提供的内容，会明确结束本条，不删除已有核心材料来迁就新内容。

两个动作有不同的工具说明。适配器请求显式设置单调用；若服务仍返回两个合法补证调用，合成同一轮有界补证处理。混合提交、多次提交或非法工具不会获得额外权限。

每条最多3次逻辑模型请求，包含格式纠正和补证后的判断；没有合法提交就记“模型未提交判断”。这是明确执行边界，不是模型复核成功的替代标准。

### 程序推进与部分交付

- 当前条的格式、引用或重复补证失败不会卡住下一条。全局取消、原期限、共享费用保护、平台不可用、凭据或来源完整性异常仍终止整个任务。
- “支持/不支持/待验证”只来自模型实际提交。材料不足、未提交、请求失败、取消、超时是独立执行状态，没有伪造的`needs_verification`意见。
- 程序直接汇总已提交的意见，不再要求模型最后调用总提交。未完成条目保留原分析意见，并显示“尚无复核结论”；任务可保留部分报告，但不标为完整完成。
- 初稿没有问题时，用独立概览条目核对已提供材料，不制造问题；报告仍保留空findings。
- 每条结束后生成不覆盖的`review-checkpoint-001.json`等文件，登记哈希和下载入口。进程中断后保留检查点，不自动续发调用。

### 期限、路由、用量与兼容

所有单条会话共用原复核180秒绝对期限，与分析300秒共同受父任务480秒限制；不按条重置。每请求每平台最多一次，切到备用后后续条目保持备用，共用原费用记录和保护。费用事件增加`case_id`与实际会话身份，汇总会话不丢失失败/未知尝试。

每个平台实际发送前记录适配器请求中的工具名称、schema摘要、安全参数、messages、条目和会话身份；不记录API key或鉴权头。离线检查将这些记录与实际进入completion替身的参数逐项比对，包括工具schema摘要和timeout。它验证客户端请求对象，不代表已经验证远端平台接受新参数。

新建双角色分析任务登记`readonly_analysis_review_v2`。旧v1工具、旧记录及幂等请求保留；已有请求身份不会被重新解释为v2。单分析和固定题单/双/三角色实验流程保持。

## 后续修复流程的需求确认（尚未实现）

用户进一步明确：启动修复后希望系统围绕整体任务改到可验收，不要求用户逐条勾选技术问题；“一个改、另一个查”应该是可多轮循环，不限制为一次返工。整个任务必须有总时间、最大轮数和无进展保护，避免持续空转。本节只更新后续设计，不修改运行代码或启动模型。

拟定流程：用户给出使用目标 → 程序整理完成条件和已核实的问题 → 修复者在副本修改 → 程序运行可用检查 → 独立复核者核对目标、改动和检查结果 → 未完成项退回修复者 → 再检查和复核 → 达到完成条件后交用户验收。

- 不要求用户逐条挑选问题。以本次使用目标为范围，一并处理确认的问题和修复引入的问题；分析中的误报先排除，不把每条候选都当作必须修改。只有功能含义不明、需要用户做实际业务决定时才询问。
- 两个角色可以多轮往返，由程序保管同一份目标、待解决事项、版本和检查记录，避免每轮重新讨论目标或反复翻旧材料。各轮修改与复核意见保留，支持回到已有可用副本，不覆盖原代码。
- 完成需要目标对应的必要检查有实际结果，并且复核没有未解决的阻塞问题。两个模型同意不等于任务已经可用；检查无法运行或依据不足时保留未验证状态。
- 暂定可调的首版设计为最多3轮“修改＋复核”、修复任务累计最多15分钟（不含此前独立分析任务），提前完成就提前结束；这些是待实现和离线检查的候选默认值，没有授权新的付费任务。程序共享绝对期限，并为检查/复核留出时间，不让换会话、换角色或进入下一轮重置计时。
- 连续两轮没有新的有效改动、实际检查改善或已解决问题时提前停止。只重复读取、换说法或修改与目标无关的文件，不算进展。
- 达到轮数、期限、平台不可用、取消或完整性异常时停止，交付最后合法副本、已完成项、未完成项和停止原因；明确本次未完成，不把停止当验收通过，也不自动另开付费任务追成功。总期限用于限制运行时间，不能保证所有任务必然在期限内修好。

现有固定题修复在`collaboration_store.py`中仍按repairing→reviewing→revising→final_review安排固定阶段，仅首审request_changes会返工；总期限已有，但多轮不能只改一个数字，需要扩展阶段/轮次、版本绑定、反馈闭环和部分成果规则。用户上传代码后的修复入口仍待接入，不能将本节说成已实现。
