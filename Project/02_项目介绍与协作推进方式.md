# Mini SWE Agent：项目介绍与协作推进方式

更新：2026-10-05。依据本轮查阅的官方仓库与文档；具体实现以之后锁定的 commit 为准。本文是入门介绍和建议路线，尚未安装项目或运行实验。

## 项目做什么

Mini SWE Agent 是一个开源的软件工程 Agent。给它一个代码仓库和任务，它可以借助语言模型决定下一步，通过命令读取文件、搜索代码、修改实现和运行测试。SWE 是 Software Engineering（软件工程）的缩写。

项目本身提供控制循环、模型接口和执行环境，实际理解和生成代码的能力来自接入的语言模型。官方当前文档为 v2，强调核心 Agent 类约百行；整个项目还包括环境、模型适配、运行脚本、配置和测试，不能理解为整个工程只有百行。[官方仓库](https://github.com/SWE-agent/mini-swe-agent)

## 用一次修复任务理解流程

假设任务是“购物车为空时计算总价报错，请修复”，这是教学示例，不是已运行的任务。

Agent先查看仓库结构、寻找总价计算函数，读取相关实现和测试，再尝试重现问题。它根据输出修改代码，运行相关测试；如果仍然失败，就把新错误作为下一步决策的依据。任务提交或达到配置限制后退出。

基本循环是：任务与历史 → 模型选择动作 → 环境执行动作 → 输出加入历史 → 下一次模型决策。[官方控制流](https://mini-swe-agent.com/latest/advanced/control_flow/)

模型认为完成只表示执行流程结束；修改是否正确还要看测试和对应评测结果。

## 几个组成部分

| 部分 | 普通话解释 |
| --- | --- |
| Model：模型 | 理解任务、解释代码、选择动作、生成修改 |
| Agent / Harness：控制程序 | 把模型调用与动作执行连接起来，管理循环和配置的限制 |
| Environment：执行环境 | 真正读取和修改文件、执行命令，返回输出 |
| Messages / Context：历史与上下文 | 模型本次决策所能看到的任务、已有动作和结果 |
| Trajectory：运行轨迹 | 保存本次执行过程，便于复盘模型为何采取某个动作 |

官方极简设计以 Bash 命令作为主要行动接口：搜索、编辑和测试通过命令完成；默认历史按步骤追加。执行环境可以采用本地或容器等方式，具体选择要看本机条件。[官方设计](https://mini-swe-agent.com/latest/)、[执行环境](https://mini-swe-agent.com/latest/advanced/environments/)、[输出文件](https://mini-swe-agent.com/latest/usage/output_files/)

## 与旧项目的联系

旧项目处理医疗知识查询，工具主要查图谱和原文；本项目处理软件任务，工具主要查看代码、修改文件、运行测试。两者都有“决策—执行—反馈”的流程，但验证答案的方法不同：这里可以用修复测试和回归测试判断代码修改。

可迁移的是预算、停止条件、状态和失败分析等工程经验。是否增加规划、上下文压缩或其他模块，要从Mini SWE Agent实际失败中判断。

## SWE-bench、baseline与我们自己的贡献

SWE-bench是软件工程任务评测集，原始任务来自真实GitHub问题。可以把它理解为配有代码仓库、问题描述和评测条件的试题集。[SWE-bench官方说明](https://www.swebench.com/)

Mini SWE Agent负责尝试解题，SWE-bench评测负责判断补丁是否解决问题。官方提供单题和批量运行入口，但产出补丁不等于已经完成评分。[运行与评测入口](https://mini-swe-agent.com/latest/usage/swebench/)

Baseline就是尚未加入我们改进的参照版本。先固定任务、模型、环境和预算，记录原版表现，再与改进版比较。

我们的工程贡献逐步形成于：可复现运行与评测、失败轨迹分析、针对问题的机制设计、公平对照、成本与退化分析。上游实现与我们新增内容应明确区分；上游排行榜成绩不能写成自己的成绩。

## 建议分工

| 工作 | AI承担 | 用户参与 |
| --- | --- | --- |
| 理解项目 | 用例讲解、关键源码导读、梳理流程 | 用自己的话解释流程，提出不清楚的地方 |
| 环境与运行 | 核对依赖、准备配置、排查错误、记录复现方法 | 提供必要资源，说明时间与费用约束，完成账号等本人操作 |
| 评测与失败分析 | 收集轨迹、评分与分类，提出证据支持的候选问题 | 一起阅读代表案例，理解失败发生的位置 |
| 改进开发 | 提供方案、实施代码、测试并解释取舍 | 理解设计理由，逐步参与关键代码和小改动 |
| 结果与面试 | 整理结果、图表、README与问答 | 判断结论是否理解，练习讲述并明确个人贡献 |

不要求用户先独立学完全部基础；按当前任务补知识。每阶段结合一个真实例子、少量关键代码和一次可检查的结果学习。

## 建议推进阶段

1. **认识项目并跑通一题。** 产出固定版本、启动方法、完整轨迹；能解释模型和环境怎样连接。
2. **跑通少量任务及评分。** 先1～3题检查流程，再视预算扩到5～10题；区分环境故障、执行完成和真正修复。
3. **建立小规模baseline并分析失败。** 可参考10～30个固定任务，根据成本和运行条件调整；找到重复出现、可修改、可测量的问题。
4. **选择一个主要改进。** 候选包括代码定位、上下文选择、失败后调整或重复动作控制；一次优先验证一个假设。
5. **做对照与必要消融。** 保持任务、模型和预算可比，记录成功率、成本、步数及退化案例；无提升也如实分析。
6. **整理实习成果。** 形成复现说明、架构解释、结果和案例、贡献边界及面试讲述。

阶段按成果推进，暂不承诺具体周数。第一个改进方向目前未定，文档也不代表已经批准付费实验。

## 最近一步

先把一次任务的运行流程理解清楚，再检查本机条件并选择最小运行方式。模型、预算、版本、任务集和评测规模在实际启动中逐项明确。
