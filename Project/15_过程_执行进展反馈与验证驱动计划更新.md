## 从什么问题出发

13轮解决了请求空间超限，却出现“已有诊断、反复阅读、迟迟不修改”的问题。任务工作记忆保存模型的假设和下一步，但无法依据实际动作判断计划是否执行、验证是否仍适用于当前代码。本轮实现一个单Agent的小模块，让程序根据源码版本和已执行的测试更新下一步建议。

## 前后流程

以前：模型生成命令 → 执行与输出归档 → 保存近期观察和模型笔记 → 压缩历史后继续请求。重复读取检测只对可识别的相同读命令生效，换行号、搜索或脚本就可能继续消耗调用。

现在：模型生成命令 → 执行与完整输出归档 → 核对实现代码版本 → 识别声明的测试及结果 → 更新当前验证状态与下一步建议 → 将精简反馈放入下一次请求。原来的上下文参数和重复读取保护保留；开启/关闭反馈由新配置选择，原版仍为默认。

模块采用以下规则：

1. 只有实现目录内容哈希变化，或同一源码版本出现新的可识别验证结果，才重置无进展动作计数。换读范围、写模型笔记、改临时脚本、重复相同测试但耗时变化，不会重置。测试/元数据变化不会被算成实现进展；这些文件仍由外部保护检查约束。
2. 连续8个已执行动作没有上述进展，就在后续请求中提醒：执行具体复现或最小修复；若证据不足，明确缺哪项，只补充那项。它是提示，没有新增总调用限制，不强制修改、不拦截合法探索；原来的重复读取停止规则仍独立生效。
3. 两组验证命令来自任务manifest与固定问题检查：原有针对性测试、问题检查。匹配声明的测试选择，识别unittest/pytest摘要并结合退出码；结果为passed、failed或unknown。空测试、全部跳过、只有成功宣称、退出码与摘要矛盾、超时、模糊命令链不能获得通过状态。过滤或其他测试选择不能代替声明的完整检查。
4. 每条验证关联当时实现版本、动作序号、完整输出路径和部分失败标识。源码再改，旧结果标为stale。模型笔记、脚本打印和Agent提交都不能替代独立验收。
5. 当前版本测试失败 → 建议查看失败证据、修订假设、最小修复、重测；实现已修改但检查缺失/过期 → 建议运行缺失检查；两组当前检查通过 → 建议审查diff和约束后提交；未改实现 → 建议复现或把充分诊断转成最小修改。建议发生变化时增加plan_version。

这是“验证驱动的下一步建议”的第一版，属于计划模块的一个小部分。它没有独立的模型规划调用，也没有自动执行/修订完整任务计划、可靠恢复、长期记忆、仓库检索或任务服务。

## 冻结对照与运行限制

本轮预定顺序：复制题旧候选 → 复制题开启反馈 → 路径题旧候选 → 路径题开启反馈，每组一次，不看结果调参或重跑选优。旧候选作为同期对照，不拿13轮历史费用/模型状态当作本轮对照。任务检查公开且可见，两题来自同一仓库，又已经用于机制设计；本轮不具独立留出评价意义。

最初自动审批两次拒绝启动同一组付费运行：首次仅认可当前可见的AGENTS.md更新请求；读取来源对话原始用户消息后，审批仍未接受跨对话证据。拒绝期间没有绕过或发送API请求。随后用户在当前对话直接回复“授权四次运行”，执行获准并完成全部预定运行，没有额外重跑。此阻塞已解除，不需要再次确认本轮已授权内容；未来余额/API不可用时仍按14的结构化原因停止。

仍需注意：8动作只是启发式提醒，不能判断所有代码阅读有没有价值；文件变化可能是不正确改动；测试摘要可能不完整，有限解析器可能漏掉合法命令。验证状态是程序观察，不是可靠安全边界。最终成绩依然由冻结原件的外部测试、文件保护、全量回归和干净副本补丁重放决定。新模块保持显式候选，不提升为默认。
