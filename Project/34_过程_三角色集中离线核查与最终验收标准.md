## 完整验收的固定标准

先分别回答三个问题，避免把它们混成一个“成功”。

| 层次 | 通过条件 | 不通过时如何记录 |
| --- | --- | --- |
| 程序流程是否正常 | 角色按约定顺序执行；交接、引用、版本、用量完整；合法批准可直接结束，合法请求修改最多返工一次；取消、超时、协议失败能停止并保留已得结果 | 具体阶段和实际原因；不得自动追加任务或恢复旧身份 |
| 该题是否修好且审查通过 | 问题检查和针对性检查通过；全量无超出原baseline的新失败；干净重放通过；最后合法审查为approve | 补丁通过而审查失败时分别显示；insufficient_evidence是有效结论，但不计“修好且审查通过” |
| 增加这套流程是否有用 | 新题、同题重跑的原baseline与完整多Agent比较，全部预声明槽位与失败都保留 | 当前没有这个结论；一次熟悉题诊断不得算效果提升 |

一次最终真实接入验收只用已熟悉的公开`split-after-boundary`题及原明确文档问题，用于检查接线，不能作为新题评价。文档缺少行为定义时允许明确未知；不能为了通过要求模型从changelog推导不存在的规范。

成功分支允许两种合法路径：

- 文档查阅 → 修复 → 首审approve → 结束；修订及最终核查应跳过。
- 文档查阅 → 修复 → 首审request_changes → 原会话返工一次 → 最终核查 → 结束。最终仍要求修改或证据不足时如实结束，不开启第二次返工。

前置离线检查、一次真实结果和页面使用证据分别保留。允许当前题未通过；不把失败都称为程序缺陷，也不因模型没批准就不断修改代码或重跑。确有新程序缺陷时，先集中离线复现并修复，再重新确定验收范围。
