## 用户现在能做什么

在原面板创建新任务时，切到真实运行，可勾选“开启任务计划与要求补充”（默认关闭），填写目标、每行一个步骤及额外约束。开启后，任务卡和新运行在同一数据库事务中保存；重复请求沿用原身份，改变初始任务卡不能复用同一请求键。

选择这类任务后，会看到“任务计划与要求补充”区域：目标、步骤状态、阻塞、下一步和当前补充要求。排队或运行中可以保存新版本；两个页面同时修改时，后保存者会收到冲突提示，不能覆盖前者。取消中、已结束及历史任务只读。

步骤状态由用户维护，包含未开始、进行中、受阻和已完成；最后一种仍明确标注“人工记录”，不等于程序验收通过。实际运行阶段、独立修复结果和审查意见保持各自原有含义。本版不自动生成或更新细粒度计划。

每次新的模型调用会读取当时最新的整张任务卡。补充要求不会打断在途请求，也不会单独增加一轮调用、延长时限、重启任务或重放旧调用；若任务已经没有后续调用，保存的要求可能没有被读取。页面会按版本显示调用记录，区分“准备中/发送情况未确认”“本次未发出”“尝试调用但响应未知”“已有模型响应”。已有响应也不证明模型遵循要求。

原入口为根目录`启动任务面板.cmd`及`http://127.0.0.1:8765`。本轮已恢复当前代码的隐藏本机服务并核对健康与新资源，无新正式任务。真实任务会按原路由产生模型费用；本轮没有在正式服务中点击创建。

## 实现怎样接入原流程

| 文件 | 本轮改动与作用 |
| --- | --- |
| [task_cards.py](../scripts/task_cards.py) | 新增任务卡校验、原子初始化、版本保存、冲突控制、只读查询、请求投影和成果导出；无独立模型客户端，无恢复入口 |
| [task_service_store.py](../scripts/task_service_store.py)、[collaboration_store.py](../scripts/collaboration_store.py) | 新增可选`task_card`创建参数；默认不改变旧创建内容，启用时追加种子哈希和功能标记，同事务登记运行与任务卡 |
| [collaboration_panel.py](../scripts/collaboration_panel.py)、[task_service.py](../scripts/task_service.py) | 原创建入口允许任务卡，新增原认证下的GET/POST任务卡路由及JS资源；保存前检查已配置凭据，不回显密钥 |
| [task_service_worker.py](../scripts/task_service_worker.py)、[collaboration_runtime.py](../scripts/collaboration_runtime.py) | 单Agent和角色模型复用同一个TaskCardModelMixin。只在API请求视图末尾追加当前用户任务卡，保留原任务和原始聊天轨迹 |
| [collaboration_live.py](../scripts/collaboration_live.py)及单Agent worker | 成果中可选导出`task-card.json`，含全部版本和调用投影记录，纳入原成果哈希/凭据检查 |
| [task_card_panel.js](../scripts/task_card_panel.js)、[task_panel.html](../scripts/task_panel.html) | 创建开关、编辑区、版本与调用状态。使用textContent及输入值显示用户内容，轮询保留未保存编辑，切换运行清空原任务内容 |
| [document_agent_demo.py](../scripts/document_agent_demo.py) | 既有离线演示允许注入任务卡；读取真实工具消息，不再假设API视图的最后一条消息一定是工具回执 |

核心入口：`validate_card()`限制字段、步骤和内容；`update_card()`使用revision比较，防止旧页面覆盖；`begin_input()`为每次调用固定当前版本、唯一input_id和投影哈希；`TaskCardModelMixin`接通原模型路径；`export_card()`保留历史版本和对应输入。

投影内容带有任务卡版本、当前内容哈希和唯一输入ID，原角色请求摘要也会包含该视图。模型仍只具有当前角色的原工具；任务卡不能修改被冻结的问题、文件权限、费用路由、阶段时限或独立评分规则。

任务卡规范JSON整体最多2048 UTF-8字节，完整单条请求视图不超过4096字节；实际请求仍接受原16KB/可选审查32KB硬保护。任务卡不会放大本地限额，无法容纳时在原保护停止，相关记录保持“未发出”，不预扣新费用。

调用记录在模型查询外层收尾，避免将本地保存凭证失败当成模型服务错误而切换平台重发。平台响应与是否正确解析/遵循要求分别记录；无响应时不补造收到或已执行。

## 存储与历史边界

新增三个附加表：当前任务卡、不可覆盖的任务卡版本、每次模型输入记录。仅首次明确创建启用任务卡的运行时才初始化，并先做一致性SQLite备份；普通服务启动、旧记录读取及默认关闭的创建不触发这次迁移。

没有给旧52条记录批量补计划或修改payload。本轮正式库没有启用该附加表，实际初始化和保存全部在隔离temp库验证。原基线与旧单/多Agent任务默认不附加卡片；新运行启用卡片时明确记录互动功能范围，不计入原冻结baseline比较。

当前不开启进程重启恢复、不恢复旧实验身份、不自动续跑、不自动执行任务卡脚本。修复者仍是本机Bash，任务卡不等于新增OS沙箱。工具/Skills插件和新厂商模型适配未在本轮实现，仍按35的后续阶段推进。

## 本轮只做的基本检查

1. 临时脚本核对：旧记录只读且不初始化任务卡表；带卡创建幂等；陈旧版本拒绝覆盖；过长卡拒绝；取消后不可编辑；单Agent实际模型适配读取最新卡；原消息超限在传输前停止。
2. 复用原五阶段演示一次走通文档查阅→修复→首审→一次返工→复核。在首审开始前将任务卡从第1版更新为第2版，后续实际请求视图均读取第2版。所有模型响应和用量固定；文件修改、本机检查及干净重放实际执行。最终问题10/10、针对性4/4、全量659/660，保留原计时失败；不是新的Agent解题成绩。
3. 使用5项已有基本兼容检查，实际全部通过：旧创建幂等、API认证、创建/取消、六个只读工具和原平台切换。不新增正式测试文件，不跑完整默认回归、适配回归或新题批次；34的301/405结果仍是旧代码的历史回归，不能挪作本轮成绩。
4. 在应用内浏览器实际点击临时预览：任务卡保存到第2版、从表单创建带卡任务、切换后内容清空/恢复、取消后只读；随后将两个临时排队任务取消，并关闭预览服务。该服务没有Supervisor、worker或模型客户端，不读取.env；即使表单mode字段为live，也只在temp登记队列，没有真实模型执行。正式8765服务未创建任务。

第一次演示检查实际失败：旧的预设回复代码通过“最后一条API消息”取证据，新增任务卡后该位置成为用户卡片，导致脚本回复生成失败。已将该演示改为查找真正的工具回执，原失败目录/日志保留；修正后同一基本脚本通过。这是离线回复夹具兼容问题，不把它记为平台故障或新版真实模型失败，也没有为此发起真实复验。

最后补齐唯一输入ID的关联后，仅用两次mock调用定向核对第1/2版与输入记录ID一一对应、原始消息不变；没有再重跑整个五阶段。五阶段目录保留当时冻结源码，最终源码另存；不能把两种检查混称为最终代码的真实全链路成功。

过程目录为`temp/harness_task_cards_20261026/`；正式源码、基本检查与临时界面凭证另封存至`experiments/harness_task_cards_20261026/`，不覆盖旧成果。原data/configs/evaluation/experiments保护文件及52条正式payload、2016条共享账本请求在收尾时核对；0真实模型调用，未动医疗项目。

原面板恢复后，Windows会锁住服务运行锁文件；该锁不计为逐字节核验通过。收尾报告单列被占用的`server.lock`/`worker.lock`（若有），其余业务文件、旧成果、正式payload与共享账本逐项核对，不为读锁文件强停正常服务。
