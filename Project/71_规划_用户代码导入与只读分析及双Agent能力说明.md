# 用户代码导入、只读分析与双 Agent 能力说明

## 后续实施状态

2026-10-30用户批准后，A1导入/A2只读报告已在1.1.0实现，实际证据和限制见[72](72_实现与验收_用户代码导入与只读分析.md)。以下保留实施前的规划口径；A3分析＋独立复核仍待。原三角色修复实验一直保留，不能把新单角色分析理解成删减旧三角色。

日期：2026-10-30。现场源码版本：`11caf4c`，开始核对时主项目工作区干净。本文是规划和现状说明，不表示新增功能已经实现。

## 用户目标与本轮边界

用户希望提交自己的代码或仓库链接，让应用自行分析，而不是从固定题目中选择。用户已进一步明确：先给出有文件位置和依据的问题报告，修复由用户另外启动。

因此下一版的主要交付目标是“用户代码 → 有依据的只读分析报告”。v1.0.0已经完成的固定任务工程验收继续有效，但它没有完成这个使用场景。旧题库保留为演示/开发回归入口，不继续占据产品首页。此次只规划、核对源码和整理文档，不开发、调用项目模型、安装依赖、读取用户新项目或重启服务。

## 用户实际使用流程（拟议）

1. 首页选择上传代码文件/项目ZIP，或粘贴公开GitHub仓库链接。文件夹可先压缩成ZIP。私有项目可先用上传方式；私有仓库授权、Gitee/GitLab和子模块另行接入，不要求用户在URL中填写token。
2. 可填写关注问题，例如“梳理登录流程”“找会导致任务中断的问题”。不填写也能开始，默认梳理项目结构、主要调用流程和有依据的明显问题。
3. 本机准备代码快照并展示目录、版本、将允许模型读取的范围和排除项。用户可缩小目录。开始分析时清楚说明所选代码片段会发送至当前模型平台并产生用量；不把整个压缩包直接发送给模型。
4. 模型按需读取、搜索代码，生成报告；大仓库分范围分析，显示实际覆盖和未覆盖部分，不承诺一次全仓逐行读完。
5. 报告中点击文件位置可回看当时的原始代码。未来再接基于该快照的追问，以及由用户另外启动的修复任务；首版分析不会自行进入修复。

拟议报告至少包括：项目用途与结构、主要执行流程、按影响排序的问题、修改建议、需要进一步验证的疑点、分析覆盖范围和未验证项。每个问题记录文件/行号/代码版本、具体触发条件、影响、引用片段、推理依据及确定程度；行号和引文由程序核对，问题含义仍可能被模型误判。“有源码依据”“模型复核支持”“实际运行验证通过”分别显示。

示例：指出 `src/auth.py` 某行的空值处理缺口，说明在什么输入下可能报错、依据是哪段调用关系、建议怎样验证。不能只写“建议加强健壮性”，也不能没有依据就生成一串漏洞或用“没发现问题”代表代码安全。

## 第一步需要改变哪些内部假设

| 当前假设 | 新分析入口需要的行为 |
| --- | --- |
| `task_workspace.py:load_task/prepare_task` 读取提前登记的manifest、issue和checks | 接收用户输入，形成独立来源快照；不要求用户自行编写题目清单、正确答案或验收测试 |
| `task_service.py:do_POST` 只接收最多8192字节JSON | 单独实现有大小/中断限制的文件上传入口，不能把大文件塞进旧JSON接口或直接放大全部请求上限 |
| `create_panel_run/create_collaboration` 限定目录题目和修复模式 | 新增独立的analysis任务种类及报告状态，保留旧repair/replay兼容；不伪装成固定题目来绕过校验 |
| 原流程先复现已知失败，再修复并评分 | 新分析通常没有已知失败或预置答案；完成标准改为报告可追溯、覆盖真实、未知明确，不套“修复通过”字段 |
| 原审查者围绕候选补丁、原问题和程序报告工作 | 新代码分析需要审查原始仓库；没有补丁时也能开展，不能直接给旧补丁审查工具换一个角色名称 |
| 原检索以Python实现路径和固定manifest为范围 | 检索绑定新快照和允许文件；先提供文本/目录搜索，Python可复用AST，其他语言不因文件可读就宣称有符号级完整支持 |

优先复用现有队列、幂等身份、取消/超时、历史、费用路由、受控读取、版本和引文核验。分析报告及输入来源另立合同，避免把已有修复编排全部搬进第一版分析。

## 只读分析的实际边界

- 上传原件与分析副本分开，原文件字节保持；只读角色只具备目录、搜索、行段读取和提交报告工具，没有Bash、写代码、执行测试、安装依赖或向任意地址发请求的工具。保存报告和日志由程序完成。
- 仓库里的README、AGENTS、脚本及提示词是被分析的资料；不能凭这些内容扩大本应用权限、运行命令或外发其他文件。没有执行用户代码的需求，第一版无需为了分析强行搭建Docker运行环境。
- ZIP接收处理路径越界、链接、Windows文件名碰撞、压缩异常和总量限制；上传失败保留清楚原因，不覆盖现有项目。只支持明确的文件格式，不自动解包嵌套压缩包。
- 默认排除真实.env、凭据/私钥、Git元数据、依赖目录、生成物、运行数据和大体积日志；识别到疑似凭据的文件先隔离并提示。自动筛选不能保证发现全部敏感内容，允许范围在分析前可见，后续读取也不能越界。
- 仓库链接先固定到具体commit或下载版本，记录原URL、获取时刻、文件清单和哈希。只允许登记的公开托管来源，校验下载重定向，不自动递归抓取子模块、LFS或README中的链接。
- 不运行测试时明确显示“未运行”；没有测试或模型不理解时仍可返回有边界的报告。报告完成不等于仓库通过测试或不存在缺陷。

上传体积、解压总量、文件数量、单文件及请求上下文限制均由程序配置；开发时按当前电脑实际压测固定，不把未经测量的数字当作已验证能力。

## 当前 dual agent 究竟是什么

准确定位：程序串行编排的“修复者＋只读审查者”，针对现有固定问题修补代码，并在必要时让原修复者返工一次。两个角色使用同一路由下的模型、不同会话；修复和返工沿用同一个作者会话，最终审查另开受控审查会话。分开上下文不能保证判断正确或误差相互独立。

```mermaid
flowchart LR
    Q[固定问题与源码副本] --> A[修复者修改并提交]
    A --> T[程序封存版本与运行检查]
    T --> B[只读审查者看问题/补丁/源码/检查报告]
    B -->|通过或证据不足| F[保存结论与独立修复结果]
    B -->|请求修改| R[原修复会话返工一次]
    R --> T2[新版封存与程序检查]
    T2 --> B2[新审查会话最终核查]
    B2 --> F
```

| 环节 | 实际能够做什么 | 主要依据 |
| --- | --- | --- |
| 修复者 | 在固定任务副本读代码、运行命令、修改已有实现并提交；受现有时间/上下文/进展保护约束 | `collaboration_live.py:make_repair_session/repair` |
| 程序检查 | 冻结候选源码和补丁，运行已登记的问题/上游检查，比较原基线，必要时干净重放 | `collaboration_live.py:seal/finalize` |
| 审查者 | 使用受限只读工具查原问题、diff、候选源码及已有报告，提交问题、位置证据、影响、覆盖和未知；给出approve/request_changes/insufficient_evidence | `review_tools.py:ReviewEvidenceBroker`，`collaboration_protocol.py:Finding/ReviewReport` |
| 返工 | request_changes才将意见交回原作者会话；保留v1和v2，最多一次返工，不循环到成功 | `collaboration_store.py:complete_role`，`collaboration_runtime.py:RepairSession` |
| 结果 | 审查结论、程序修复验收、协作是否完整分开；审查通过不能覆盖程序失败，审查失败也保留合法候选与已有检查 | `collaboration_store.py:finish`，`collaboration_live.py:finalize` |
| 裁决 | 仅对开发者登记并映射的具体检查核对某条意见，不能把任意自然语言审查判断成客观真值 | `review_adjudication.py` |

普通dual默认配置为 `configs/multi_agent_v1.json`：父任务1800秒，初修/首审/返工/终审300/120/180/90秒，一次反馈窗口；审查不具备任意Bash或自行运行测试的能力，测试由程序执行。不是并发写代码、动态分工、两个模型投票，也没有任意仓库通读入口。

还发现一处需要在后续开发中明确的配置差异：普通dual读取multi_agent_v1，三角色读取multi_agent_documents_v3；后者声明32KiB审查视图和declared_checks_v1修复进展政策，普通dual配置没有这些字段，相关调用方按条件启用。因此近几轮完整组三角色的行为和成绩不能直接当作普通dual的当前能力或净收益。这里是现状核对，不在本轮修改参数或补规则。

## 现有真实证据支持到什么程度

- [25](25_过程_双角色模型接线与离线反馈验收.md)：一个固定开发题真实初修和独立首审通过；审查直接approve，未触发返工。
- [28](28_过程_真实反馈诊断与原会话返工验收.md) 的最终身份 `d3173d4153e544ccbf0eb066834848f8`：真实首审request_changes、原会话返工、新版登记、最终approve及重放完整通过。但初始候选由人工提供、缺陷已知，并非证明模型独立发现未知bug；原先失败都继续保留。
- 近期完整组三角色比较包含成功和失败；例如63两题中改良单Agent和完整组三角色都是2/2，64中两组都是0/4。这些样本不能当普通dual单因素对照，更不能证明一般情况下多一个审查角色就更好。
- [70](70_审查与发布_本机工程首版.md) 的最新真实接入是single/raw，不能写成最新普通dual真实验收。

因此可以说“修复—审查—一次返工的工程流程已实现，有历史真实接入证据”。目前不能说“审查必定发现遗漏”“两个Agent稳定优于一个”“可对任意用户仓库准确完成分析”。

## 如何服务于新的用户代码分析

新只读分析首先应独立可用。建议把双角色分析作为后续可选能力：分析者先梳理项目并给出候选问题，复核者围绕原代码核对每条问题的依据、触发条件和反例，支持、驳回或标为待验证；最终报告保留这些区别。复核者不是只对第一份报告换个说法，两角色都不修改代码。

这需要新的analysis/report协议，不能直接复用当前“作者先改代码、审查补丁”的dual产品含义。现有双角色修复流程可以继续作为以后用户主动发起修复的参考；用户未启动修复时不会触发它。

## 实施顺序与完成标准（全部待开发）

| 步骤 | 可交付内容 | 验收重点 |
| --- | --- | --- |
| A1：接收用户工程 | 文件/ZIP上传、公开GitHub链接、快照与范围预览；首页不再要求选固定题 | 两种来源都能导入；原字节不变，恶意路径/超量/下载失败明确处理；旧回归题和历史保持 |
| A2：只读分析闭环 | 按需阅读、结构/流程说明、带精确位置的问题报告、未知/覆盖/费用/取消 | 至少实际跑通一个上传工程和一个链接工程；检查引用真实、无源码写入/命令执行；没有预置测试也能诚实完成报告 |
| A3：可选双角色复核 | 原代码核对、反例/误报处理、分开记录单/双模式成本与结论 | 保留争议和未验证项；同一输入比较时控制其他策略，不能以多角色通过计数证明收益 |
| 后续单独范围 | 同快照追问、私有仓库账户连接、更多托管平台、用户主动启动修复 | 分别按需求接入；执行测试/修复前另做运行环境和权限设计，不让这些后置项阻塞A1/A2 |

用户需求已足够确定，可以按A1/A2细化开发；下一次开始实现前只需重述实际支持范围和必要外发材料，不再要求用户选择技术框架。本轮不启动开发或真实模型调用，保留现有v1.0.0与其发布产物。
