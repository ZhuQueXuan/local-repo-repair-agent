# API优先级与备用平台切换

日期：2026-10-13。

用户要求：先使用新提供的北邮网关key；首选不可用时，再使用本项目原有的DeepSeek官方key。两套凭据仅保存在本项目私有`.env`，旧key、原官方地址和模型保留，没有把密钥放入代码、文档、日志或正式成果。

## 已实现的行为与实测结果

首选：用户提供的`https://myai.bupt.edu.cn/llm-gw/v1`，模型`deepseek-v4-flash`，凭据字段`BUPT_API_KEY`。备用：原`https://api.deepseek.com`，模型`deepseek-flash`，凭据字段`DEEPSEEK_API_KEY`。

随后按用户反馈统一配置位置：首选的URL、模型和key都在私有`.env`，对应字段为`BUPT_API_BASE_URL`、`BUPT_CHAT_MODEL`和`BUPT_API_KEY`。公共策略JSON只声明这些字段名与优先级。首轮URL/模型原本在公共JSON中，并非未配置；统一后实际读取地址保持不变。

所有现有Agent入口继续共用`BudgetedDeepSeekModel`，因此不需要逐个改启动命令。新任务默认从首选开始；首选认证/权限/余额或额度/限速/模型不可用/明确服务器错误/连接超时等故障，程序尝试备用一次。本次任务切换后继续用备用，避免每轮反复尝试失败的首选；下一次新任务重新优先尝试首选。普通参数错误400、缺失用量或输出格式问题不作为换key的理由；两边都失败则停止并报告，不循环重试。

90项离线检查通过，包含已有77项及新增13项。一次真实最小连通性测试得到：

| 步骤 | 结果 | 能证明什么 |
| --- | --- | --- |
| 首选北邮网关 | 连接错误；LiteLLM归类为InternalServerError，status_code为500，没有成功用量回执 | 首选当前未连通；不能推断key失效、余额不足，也不能直接认定远端真的返回500 |
| 同一次逻辑请求自动切到官方备用 | 成功，返回模型`deepseek-flash`；工具调用成功解析 | 真实失败→自动切换→备用响应流程已通过 |
| 原计划的单独备用检查 | 跳过，因为自动切换已经验证了备用 | 避免重复请求 |
| 无凭据GET网关`/models` | ConnectError，WinError 10053：主机软件中止连接；没有发送key、没有模型调用 | 独立确认当前环境连接此地址失败；具体网络/软件原因尚未查明 |

测试只发送固定连接检查文字，最多128输出token、20秒超时，没有发送仓库源码，没有执行生成的任何命令。总共2次实际模型API尝试：首选失败、备用成功。备用305输入/41输出token，按本项目既有保守口径估算0.000938元；首选失败费用无法核对，保留0.10元未知占位，不能当作实际已扣费。

首选成功分支、额度失败切换等其他分支只有模拟验证；没有人为耗尽额度、向远端发送错误key或反复重试失败网关来制造切换。当前不能声称新key已在真实网关上认证成功；已确认的是优先顺序和实际备用切换。

## 前后流程和记账

以前：读取唯一官方key → 请求官方模型 → 请求失败就停止。

现在：读取两套配置 → 优先请求北邮模型 → 如遇可切换故障，记录失败和未知费用 → 请求官方备用 → 按实际成功平台记录用量与费用 → 返回Agent继续。任何一次失败不会清空历史账本，也不会把两次HTTP尝试算成一次。

北邮网关计费未确认。成功响应会记录token及模型，但`estimated_cost_cny`为null、`cost_status`为`unknown_platform_price`；账本保留明确标注的0.10元价格未知占位。这个值是已有保护体系的占位，不是价格上界、实际费用或官方计价。只有项目费用无上限模式允许继续未定价平台请求；未来若显式设费用上限，需要先确认网关价格。

Agent内部的`cost=0`仅表示该次没有可计入的已知价格；同步`cost_known=false`和报告中的`cost_estimate_complete=false`，不能把它描述成免费。本地统计明确区分已知估算、未定价用量和未知失败费用。官方备用继续用既有2元/百万输入、8元/百万输出的项目保守估算，不能代表平台实际账单。

如果存在未定价成功请求或失败费用，报告的整体`estimated_cost_cny`及序列化费用为null；可计算的部分另放`known_price_estimate_cny`。因此不会把只有备用已知费用的数值写成两平台完整费用，也不会将未定价网关成功写成“0元”。

本轮结束本地已知估算7.381942元；历史未知0.30元与本轮未知失败占位0.10元保留，总账占用7.781942元。没有查询或推断平台余额，不恢复旧5元/15元上限。

## 使用与局限

继续使用现有项目运行入口即可自动按优先级选择。检查配置可执行`.venv\Scripts\python.exe -B scripts/check_provider_connection.py`，它不调用API；显式增加`--run`才会进行最小真实探测。当前首选连接失败时会自动用备用，并记录故障原因；新任务会再次先试首选。

网关连接问题尚未解决，不能保证当前机器能使用新key；是否与校园网、代理、安全软件或网关服务有关还缺证据。本轮没有关闭TLS校验、擅自更换用户提供的域名，或持续探测失败服务。成功备用连通性检查不等于新的完整仓库任务成绩。

历史实验冻结清单和成果保持原样。当前代码与模型路由已经变化，旧冻结配置按设计会拒绝使用当前代码；后续实验需要新身份和完整输入清单，纳入`provider_priority.py`及公共策略配置，不重写旧清单。

本轮是用户要求的接入维护，不表示仓库检索已经实现。下一主模块仍按此前讨论推进新任务准备、仓库检索与代码定位，并保留真实验证失败后计划更新的评测缺口。

## 截图、环境字段与引号排查（同日后续）

用户提供平台截图并询问是否配置有误，随后指出.env仅有新key、旧key有引号而新key没有。逐项核对结果：

1. 截图中的Base URL与模型和程序首次配置一致。使用OpenAI SDK的离线模拟传输核对实际拼接，地址为`https://myai.bupt.edu.cn/llm-gw/v1/chat/completions`，模型参数`deepseek-v4-flash`，没有重复/v1；模拟没有发送真实key或调用模型。
2. 首轮地址/模型确实在JSON而不在.env。为统一查看和修改，已把首选URL、模型、key三个字段都迁入.env，加载器按公共策略中的字段名读取；有key但缺URL/模型会明确报配置缺失。新增3项检查后共93项离线检查通过。
3. .env的普通key有无外层引号都有效，dotenv读取会去掉外层引号。已统一新三项的双引号格式，并比较修改前后整个解析字典完全相等，证明引号变化没有改变任何实际配置值。没有输出密钥或复制私有配置。
4. 程序有效系统代理是`http://127.0.0.1:7897`，DNS返回198.18开头的地址。它与[Mihomo文档中的fake-ip范围](https://wiki.metacubex.one/config/dns/)一致，提示代理/DNS参与，但不能据此确定具体故障软件。Python默认连接失败，绕过环境代理的一次仅诊断连接仍失败；系统curl经代理和直连都在TLS握手阶段失败，未得到HTTP响应。证书校验始终保留，没有改系统代理或安全设置。
5. 用户确认浏览器能打开平台后，浏览器库存显示实际已有页面为`http://10.3.68.122:30088/apikeys`。这与截图API域名是不同入口。直接在同一Edge打开公开API域名的/models页面，得到`ERR_CONNECTION_CLOSED`；因此该API域名在浏览器也未连通，不能用“校内网页能开”证明其API域名可达。
6. 一次无key的校内对应API路径浏览器检查被客户端拦截，未得到服务器结果；没有向该HTTP地址发送用户key，没有将首选URL擅自改为HTTP内网地址。

当前能确定的是：URL和模型与截图相符，引号不影响读取；公开API域名的连接路径未通，真实新key认证仍未知。还无法分辨代理路由、域名网络入口或服务端连接策略的具体责任。后续需要确认平台当前可达的API入口和网络条件，不继续改key、关闭证书校验或反复发失败模型请求。

此后续没有新增模型API尝试或费用，原17个正式成果保持原样；93项检查、最新加载器/公共配置和无凭据诊断另存同一成果目录的`env_and_network_followup/`。

## 接入指南兼容性与校园 DNS（同日继续）

用户补充完整指南，并确认当前在校园网内。因此“校外需学校VPN”不作为本次缺失条件。指南明确支持Chat Completions，Responses兼容性未验证，且暂不支持`reasoning_effort / thinking`。

核对发现本项目接入代码确实沿用了官方DeepSeek的`extra_body.thinking`参数。这是接入实现需要修正的地方，不能归责于用户.env或key引号。已在[Provider](../scripts/provider_priority.py:18)中明确平台是否支持思考控制；[模型初始化](../scripts/run_deepseek_smoke.py:97)只为支持的平台添加参数，[切换平台](../scripts/run_deepseek_smoke.py:113)同步添加或移除。北邮请求不携带thinking，官方备用保留既有设置；继续使用Chat Completions，不因指南同时介绍Responses而更换接口。

新增一项平台参数切换检查，验证首选不携带thinking、备用恢复原设置，同时保持连接检查的输出上限和超时。94项离线检查全部通过。配置预检确认北邮首选/官方备用以及各自能力，0次API请求。尚未在真实北邮响应上验证本次参数修正。之前的错误发生在TLS/连接阶段、没有HTTP响应，参数修正不能证明该网络故障已解决。
